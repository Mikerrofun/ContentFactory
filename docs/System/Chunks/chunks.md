# Архитектура чанков (Этап 1)

Статус: черновик v2, на согласование. Дальше: 5-тактная валидация → самообучение → промпт+самокритика → учёт после человека.

Главные сдвиги:
1. **Не 6 равноправных типов, а 2 изнашиваемых ядра + 4 эталонных пула.** Износ только у ядер.
2. **3 поста в день — одного типа.** Копирайтер выбирает лучший в этом типе → прокачиваем именно этот тип (Этап 3).
3. Эталоны — это обвязка контекста; `audience` — это стиль/язык, не фактический донор.

---

## 1. Зачем типы

Один «атомарный факт» не подходит всем: у кейса ценность — сюжет, у золотого поста — стиль, у факта — цифра, у audience — язык. Тип определяет: (а) как резать, (б) какие поля, (в) изнашивается ли, (г) роль в бандле.

Жёстких типов минимум, делим по **поведению**, а не по контенту.

---

## 2. Два класса

### Класс A — ИЗНАШИВАЕМЫЕ ЯДРА (основа темы, из них якорь)
| Тип | Что это | Откуда | Износ |
|---|---|---|---|
| `knowledge` | входные данные: вебинары, статьи, расшифровки | основной поток из бота | по фактам |
| `case` | кейсы учеников | CASE (69) + новые | полный после использования |

### Класс B — ЭТАЛОННЫЕ ПУЛЫ (обвязка, MMR, не основа)
| Тип | Что это | Откуда | Износ |
|---|---|---|---|
| `fact` | проверенные факты/цифры | FACTS (71) + PRODUCT_FACTS | очень медленный |
| `voice` | золотые посты-эталоны стиля | BEST (67) + финалы | очень медленный |
| `swipe` | карточки чужих механик | SWIPES (112) | очень медленный |
| `audience` | живой язык, страхи, возражения | AUDIENCE | нулевой (словарь) |

## 3. Поля (единая схема + type-specific)

### Общие
`id`, `type`, `text`, `source_path`, `source_url`, `added_at`, `chunk_embedding`, `depletion`, `bundle_hits`, `use_count`, `last_used_at`, `status`.

### Type-specific — по каждому типу

**knowledge** (главный донор фактуры)
- `facts[]` (3-7 атомарных), `fact_embeddings[]`, `facts_used[]`
- `topic`, `cleaned` (почищен ли от разгов.мусора)

**case** (история-доказательство)
- `fear_closed[]` — см. §5
- `steps[]` (3-5 действий), `result`, `income_milestone`
- `cooldown_until` (полный износ → таймер)
- `hero_bio` (кто, контекст), `source_proof[]`

**voice** (золотой эталон стиля)
- `s_scheme` (S1-S15), `pillar`, `markers[]`
- `closing_type` (какой приём финала: лестница/факторы/мостик/CTA/арка)
- `is_human_final` (правлен ли человеком)

**swipe** (морф-шаблон механики)
- `pillar`, `format` (A-M), `why_it_works[]`, `structure[]`
- `patterns_to_borrow[]`, `do_not_copy[]`

**fact** (number-guard)
- `fact_text`, `allowed_context`, `forbidden` (что нельзя выдумывать)
- `number_value`, `period`

**audience** (стиль/язык — см. §6)
- `fear_type` (1-7 из fear_markers), `phrase` (дословная формулировка)
- `emotion` (страх/возражение/желание/успокоитель)

## 4. Нарезка нынешних и будущих

- **knowledge:** чистка → блоки 300-500 слов → LLM 3-7 фактов → эмбеддинги.
- **case / voice / swipe / fact / audience:** карточка/фраза целиком = 1 чанк.
- **Будущий новый текст:** бот → БД → (Этап 1.5) определить тип → резать по правилу → индексация.

---

## 5. fear_closed — что это и зачем (детально)

**Что:** массив в case-чанке, какие страхи аудитории кейс закрывает. Берётся из `fear_markers.md` (7 групп):
1. «не справлюсь / не освою», 2. «обманут», 3. «впустую потрачу», 4. «нет времени», 5. «нет компьютера», 6. «поздно начинать», 7. «стыдно перед другими».

**Зачем:**
- **Подбор доказательства под тему:** если тема поста про страх «поздно» → тянем case, у которого в `fear_closed` есть #6. Это точнее, чем косинус.
- **Связь с типом поста:** PROOF-кейс собирается вокруг кейса, закрывающего нужный страх.
- **Метрика пригодности:** кейс, не закрывающий ни один страх → слабый кандидат в PROOF standalone (правило из fear_markers).
- **Приоритет в бандле:** кейсы с >1 закрытым страхом идут выше.

**Как заполняется:** при индексации case дешёвая LLM/эвристика сверяет текст кейса со словарём fear_markers → проставляет `fear_closed[]`.

## 6. Эталонные пулы — детально (особенно audience = стиль)

### fact
Донор разрешённых цифр. Никогда не тема. Докидывается как number-guard: генератор видит «можно 300к, нельзя 1млн». Износ минимальный.

### voice (золотые посты)
Эталоны стиля. **Никогда не основа/идея.** Докидываются 2-3 штуки по S-схеме+тону как few-shot. Износ очень медленный. Пополняются финалами копирайтера (Этап 3).

### swipe
Морф-шаблоны: структура/механика, НЕ голос. 1 штука под PILLAR+формат. Даёт «скелет», наполнение — своё.

### audience — ЭТО СТИЛЬ/ЯЗЫК, НЕ ФАКТЫ
**Что:** банк живого языка аудитории (страхи, возражения, желания, успокоители) дословно. Из AUDIENCE.
**Зачем:**
- **Узнавание:** 1-2 фразы аудитории встраиваются дословно → «это про меня».
- **Тон:** задаёт, как думает читатель 40+ (не интеллигентные обороты, а «поздно мне уже»).
- **Не фактический донор:** ничего не «доказывает», только красит речь.
**Роль в бандле:** 2-3 фразы под главный страх темы. Износ нулевой (словарь). Основа — никогда.

---

## 7. Износ по типам

- **knowledge:** по фактам, основной износ. `(1-depletion)^α`.
- **case:** полный после использования → `depletion=1`, `cooldown_until` (долгий). Одноразовый.
- **fact/voice/swipe/audience:** почти не изнашиваются, малый штраф за присутствие. Не основа.

## 8. Сборка контекста (5 слотов)

| Слот | Источник | Сколько |
|---|---|---|
| 1. Якорь | ядро (knowledge/case) | 1 |
| 2. Факты-доноры | knowledge соседи (MMR, 0.55) | ~10-12 |
| 3. Кейс-доказательство | case по fear_closed | 1-2 |
| 4. Voice-эталоны | voice по S-схеме+тону | 2-3 |
| 5. Морф-шаблон | swipe по PILLAR+формату | 1 |
| + гард | fact + PRODUCT_FACTS | набор |
| + узнавание | audience фразы | 2-3 |

Якорь — только ядро. Остальное — обвязка.

---

## 9. 3 поста в день — одного типа

- Утро: система берёт **один тип поста** (ротация по взятым ранее типам, не по планам).
- Генерит 3 поста **этого типа** (3 разных якоря/угла из ядра).
- Gate + самокритика → 3 готовых.
- Копирайтер выбирает лучший в типе + правит.
- **Прокачиваем именно этот тип** (Этап 3): пары «было→стало» идут в правила этого типа.
- Если данных под тип нет (мало кейсов) → fallback на другой тип.

---

## 10. 5 типов постов и связь с чанками

HUMAN-история / PROOF-кейс / METHOD-чеклист / TRUST-границы / PROOF-мой путь.

Связь двусторонняя, без плана:
- Система смотрит взятые типы → берёт другой.
- PROOF-кейс → якорь case + кейс по fear_closed.
- METHOD → якорь knowledge + шаблон swipe.
- Нет данных → fallback.
